## P0：四条静默失败

共同点：**读代码看不出来，跑起来也不报错**，只是行为悄悄不对。

### 1. `migrate()` 引用了两个没定义、也没 import 的常量

`schema.js` 的 `migrate()` 用 `LEGACY_STAGE_MAP` 与 `SCOPE_SQL`，但该文件只 `import` 了
`parseTargetPort`。两处引用都包在 `try {} catch {}` 里，`ReferenceError` 被 catch 吞成
「忽略」，于是：

- 老库的 `attack_step.stage_code` 回填**从未执行**；
- 老库的 `asset.scope` 回填**从未执行**。

读侧有 `COALESCE(scope, SCOPE_SQL)` 兜着，所以故障不显形——这也正是它一直没被发现的原因。

**修法**：两个常量搬进 `schema.js`（它自称「数据形状的唯一定义处」，且是 `store-core.js`
的依赖叶子，放这里不产生循环），`store-core.js` 改成 `import` 并原样再导出，对外 API 不变。

**实测**（`/tmp/p0-test.mjs` G-1）：

```
✓ migrate() 不抛异常
✓ asset.scope 全部回填（SCOPE_SQL 可解析）
✓ SCOPE_SQL 判定正确：10.1.2.3=internal  8.8.8.8=external  100.64.1.1=internal
✓ attack_step.stage_code 全部回填（LEGACY_STAGE_MAP 可解析）
✓ LEGACY_STAGE_MAP 映射正确：vuln→internet  access→internal  pivot→boundary
```

### 2 & 3. 无靶标时的写操作判定 + 未知 op 被兜底吞成 `ok:true`

原版用前缀正则判「写」：

```js
const writing = /^(add|save|update|delete|import|assess|open)/.test(op)
```

漏了 **`shotAdd` / `shotDelete` / `assetTest` / `resetPrompts`** 四条 → 无靶标时它们走
「只读空结果」分支，返回 `{ ok: true, items: [], ... }`，调用方以为写进去了。

更糟的是同一行下面的兜底 `return { ok: true, items: [], ... }` 对**任何**未知 op 都成立，
于是 `dispatch` 末尾的 `throw new Error('unknown op: ...')` 永远到不了 —— 拼错的 op 名
静默变成「成功、空结果」。

**修法**：显式 `WRITE_OPS`（22 条）/ `READ_OPS`（32 条）集合；未知 op 在兜底之前抛。

**实测**（G-2 / G-3，共 19 个断言全绿）：

```
✓ shotAdd / shotDelete / assetTest / resetPrompts / addVuln / savePrompt / import / addScoreHit
  → 无靶标时一律「请先在顶部选择或创建一个靶标」
✓ snapshot / assets / report / prompts / shotData → 只读空结果
✓ shotAd / asstTest / nonsense / addVulnn → unknown op（有靶标、无靶标都一样）
```

**动态对账**（验收闸门 [12]）：把 `if (!id) {` 之后出现的每个 `op === 'X'` 字面量
抽出来，逐个核对是否被两个集合覆盖 —— 当前 **54 个 op 全覆盖**，两集合无交集。
上游以后新增 op 而忘了加进集合，这道闸门会立刻红。

### 4. 模板检索的 `category` / `offset` 被静默丢弃

`tools.js` 的 `redteam_poc_search` 一直在调：

```js
store.searchTemplates(q, Math.min(limit, 100), 0, args.category || '')
```

而 store 的签名是 `searchTemplates(q, limit = 40)` —— 第 3、4 个参数进不来。
**「按归类筛模板」这个已经写进工具 schema 的参数完全无效。**

同时面板按 `templates.byCategory` 的 `{ code, n }` 画分类计数，`templateStats()`
却只返回 `{ dir, total, cve }` → 分类计数永远是 0。

**修法**：

- `searchTemplates(q, limit, offset, category)`，归类判定复用 `guessPocCategory`
  （与知识库同一套关键词，不写第二份推测逻辑）；
- `templateStats()` 补 `byCategory`，每条同时给 `code`（面板用）与 `name`（工具文案用）；
- 补 `matched` / `offset` 字段，面板才能显示「命中多少 / 第几页」。

**实测**（G-4，6 条假模板：3×rce、1×sqli、1×xxe、1×misc）：

```
✓ byCategory 归类正确：rce=3
✓ offset 生效：total=6 取 offset=2 limit=2 → 2 条
✓ category 生效：rce 只返回 3 条
✓ q + category 同时生效：q=nginx + category=rce → 1 条
✓ 没有该类模板时返回空而不是报错
```

> 顺带一个发现：`weblogic-rce` 会被 `guessPocCategory` 归到 **deserialization**
> （因为 guesser 先匹配 `weblogic`）。这是**上游既有口径**，与知识库一致，不是本轮引入的。

## P1：会话 → 靶标绑定层

### 为什么要有

上游 community 的绑定是**进程内 `bindings` Map**：dsh 一重启就全没了，面板也无从知道
「我这个会话绑的是谁」，只能永远跟全局「当前靶标」指针。多会话并行时指针只有一个，
跟着它会把别人的靶标显示到自己面板上。

最讽刺的是 community 自己的文案已经写着「每个会话有自己的靶标绑定，多会话并行不会把
报告写串」——但那是纯内存态，重启即失。

### 与上游 safe 的差异

safe 有 `sessions.json`，但用 `writeFileSync` 直接覆盖。进程崩在写一半会留下半截 JSON，
而读取侧把坏 JSON 当作「还没绑过」→ **全部绑定静默消失**。

本轮改用 `atomicWriteSync`（`lib/atomic-files.js`：写临时文件 + rename，Windows 上还带
EPERM/EACCES/EBUSY 退避），读到的一定是旧内容或新内容。

### 落点

| 位置 | 内容 |
|---|---|
| `lib/redteam/store-core.js` | `sessionBindingsPath / sessionBindings / sessionBinding / setSessionBinding / clearSessionBinding` |
| `dispatch` | `sessionBinding`、`sessionBindings`、`bindSessionEngagement`（全局 op，不依赖当前靶标） |
| `activateEngagement` | 带 `session` 时顺手落盘；不带 `session` 的老调用方行为不变 |
| `lib/redteam/tools.js` | `persistRootBinding()`，接在 `redteam_engagement_open` 与 `redteam_session_bind` 两处显式绑定后 |
| `client.js` | 面板启动时先问 `sessionBinding`，有绑定就切过去；下拉切换时带 `session`；头部出现「跟随本会话」徽章，点一下解绑 |

表结构 `{ v: 1, agents: { <会话 id>: { engagement, name, at } } }`，只记**根会话**
（子智能体沿父链继承），最多留 200 条、且只留靶标还存在的。

### 实测（`/tmp/p1-test.mjs`，31 个断言全绿）

```
✓ 落盘 / 读回 / 表结构
✓ 空 session、空 engagement、指向不存在靶标 → 一律拒绝，且不留下痕迹
✓ 重复写同一会话 = 覆盖，不产生重复条目
✓ 半截 JSON → 当作没绑过，不抛；非法条目被跳过、合法条目保留
✓ 连续 30 次写入后仍是合法 JSON（原子写）
✓ 超过 200 条自动裁剪，保留最新
✓ 三个 op 全通；缺 session 报错；engagement 为空 = 解绑
✓ activateEngagement 带 session → 自动落盘；不带 session → 行为不变
✓ 指向已删靶标的绑定不再返回
```

## P2：会话 → 靶标关系图（SessionMap）

放在 **智能体页**（与 safe 同位置），但实现刻意不同：

| | safe | 本包 |
|---|---|---|
| 数据源 | 直打宿主 `/api/session/list` 内部 RPC | 自己的 `sessions.json`（`op: sessionBindings`） |
| 宿主升级 | rpcId/method 一变就**静默空白**，不报错 | 不受影响 |
| 交互 | 只读，点节点没反应 | `onPick`：点靶标直接切过去 |
| 刷新 | 轮询 | 只在 `refreshKey` 变化或手动刷新时取一次 |
| 失败 | — | 保留上次快照 + 挂「数据陈旧」标记，不假装看到的是当前状态 |
| 连点 | — | 后发先至丢弃，只认最后一次响应 |

> 注：safe 的 SessionMap 还有一处**有码无出口**——它的 `todos` 字段被宿主类型系统排除
> （`typert.host.js:3765`），第三行恒为「未提供待办」。本包不复刻这个残点，改为按
> 靶标分组展示「谁占着哪个靶标」。
