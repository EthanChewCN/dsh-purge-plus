# 审计模板（所有 audit 文档必须严格按此结构）

> 目标：**读者只读这份文档，就能把这个模块重新实现出来。**
> 不允许出现「大致」「可能」「应该是」这类措辞。凡不确定，写成 `❓未验证：<具体缺什么>` 并单列。

## 硬性要求

1. **每条结论必须带 `文件:行号`**。行号以当前 vendor 快照为准（`vendor/community` / `vendor/safe`）。
2. **区分「读到」和「跑过」**：静态读出的标 `[静态]`，实际执行/请求验证过的标 `[实测]`。
3. **区分版本**：community 1.7.20 / safe 2.0.0。跨版本对比时两边都写行号。
4. 只读审计，**不得修改任何代码**。
5. 输出简体中文；代码标识符、字段名、op 名保持原文。

## 文档结构

### 1. 模块清单
表格：`文件 | 行数 | 一句话职责 | 是否被 index.js 加载`

### 2. 数据模型
每个持久化对象一张表：`载体（文件/表）| 字段 | 类型 | 谁写 | 谁读 | 生命周期（何时创建/清理）`

### 3. 业务逻辑
按**入口**组织，一个入口一小节：
- 入口签名（op 名 / 函数名 / 事件名）
- 判据（逐条 if 条件，带行号）
- 副作用（写什么、发什么、改什么状态）
- 失败路径（抛错 / 静默返回 / 降级）

### 4. 对外接口
表格：`类型（HTTP op / agent 工具 / 事件 / slot / CLI）| 名称 | 入参 | 出参 | 调用方`

### 5. UI 触点
表格：`组件名 | 文件:行 | 依赖的 op | 展示字段 | 交互（点击后发生什么）`

### 6. 依赖
- 内部：本模块依赖哪些同库模块
- 宿主：调用了宿主的哪些 API / RPC / slot（**逐个列出，标注是否为公开 API**）
- 外部：网络请求、子进程、文件系统路径

### 7. 与另一版的差异
表格：`能力 | community 行号 | safe 行号 | 差异性质（新增/重写/删除/等价）`

### 8. 风险与脆弱点
表格：`风险 | 触发条件 | 后果 | 是否可静态检出`

### 9. 逐条功能清单
**这一节最重要。** 表格：`编号 | 功能 | 代码位置 | 状态（完整/部分/缺失）| 备注`
编号用 `模块前缀-序号`（如 `CM-UI-001`）。

### 10. 未验证项
列出所有 `❓未验证` 的条目，说明缺什么才能验证。
